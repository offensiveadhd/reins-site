Reins in Electron

Reins in Electron in full: building it in, origins, adopting an app, the two walk-throughs with Claude and Hermes, and what was tested. Rendered from docs/ELECTRON.md.

This page is docs/ELECTRON.md, rendered from the repository at build time. It is the text the project maintains, not a copy.

An Electron window is a Chromium page, so everything Reins does in a browser tab works in it: the UI tree, the app's own actions, the cursor, the consent prompt, the indicator, the panel with its permission levels, and the chat. What differs is how the page reaches a hub, and what its origin is. This guide covers:

  1. Build it in: an app you write is a surface, with no socket on the page side.
  2. Origins: what file:// and app:// pages are to a hub.
  3. Adopt an app you did not build: reins-electron.
  4. The panel and permission levels in an Electron window.
  5. Chat: the person in the window talks to the agent that drives it.
  6. Claude controls Hermes: a step-by-step guide.
  7. Claude and Hermes work together on one surface: a step-by-step guide.
  8. Security notes, Troubleshooting, What was tested.

1. Build it in #

Three small pieces, one per place Electron runs your code. The example app in examples/electron is these three pieces and nothing else.

The main process hosts the broker and decides which windows may be surfaces:

JavaScript
// main.mjs
import { app, BrowserWindow, ipcMain, MessageChannelMain, protocol } from 'electron';
import { startHub } from '@offensiveadhd/reins/hub';
import { preloadPath, reinsMain } from '@offensiveadhd/reins/electron';

// A scheme of the app's own gives its pages a real origin, app://notes (section 2).
protocol.registerSchemesAsPrivileged([{ scheme: 'app', privileges: { standard: true, secure: true } }]);

app.whenReady().then(async () => {
  // protocol.handle('app', ...) goes here: serve your files.

  const hub = await startHub({
    agents: [{ kid: 'default', key }],          // a 32-byte secret, from a file only you can read
    surfaces: { origins: ['app://notes'] },     // the origin of your own window
    surfaceSockets: false,                      // surfaces come over the port, never the socket
    policy: 'guarded',
  });

  const reins = reinsMain({
    ipcMain,
    MessageChannelMain,
    accept: (link, meta) => hub.broker.accept(link, meta),
  });

  const win = new BrowserWindow({
    webPreferences: { preload: preloadPath, contextIsolation: true, sandbox: true },
  });
  // Only this window may ask for a link, and only while it shows this page.
  reins.allow(win, { url: 'app://notes/index.html' });
  await win.loadURL('app://notes/index.html');
});

The preload is ready-made: preloadPath names one CommonJS file that needs nothing but electron, which is all a preload may load under sandbox: true. It puts one function in the page, window.reinsElectron.connect(token), and hands the port the main process sends on to the page. It keeps nothing and decides nothing. If the window already has a preload, call the same code from it (it has to be bundled into your preload, as everything a sandboxed preload uses does):

JavaScript
// your-preload.js
import { exposeReins } from '@offensiveadhd/reins/electron/bridge';
import { contextBridge, ipcRenderer } from 'electron';
exposeReins({ contextBridge, ipcRenderer });

or add the ready-made file next to yours with session.registerPreloadScript({ type: 'frame', filePath: preloadPath }) (not run).

The page asks for its link and gives it to the driver:

JavaScript
// renderer
import { createDriver } from '@offensiveadhd/reins/driver';
import { electronLink } from '@offensiveadhd/reins/electron/renderer';

const driver = createDriver({
  app: { id: 'notes', name: 'Notes', version: '1.0.0' },
  link: await electronLink(),
  policy: 'guarded',
});
driver.action({ name: 'note.add', description: 'Add a note.', risk: 'safe', params: { /* ... */ } }, ({ text }) => addNote(text));
await driver.connect();

A page without a build step imports the same two things from files of the package: dist/bundle/reins-driver.js and dist/bundle/reins-electron.js.

What you get, and what to know:

  • No socket on the page side. The link is a MessageChannelMain between your main process and your page. It works under any Content Security Policy: the example page runs with default-src 'none'; script-src 'self'; connect-src 'none'. Run (builtin).
  • The link counts as verified (SPEC section 5): the consent prompt does not carry the "unverified hub" mark, because the link never leaves your app. Run (builtin).
  • surfaceSockets: false closes the hub's socket to surfaces. Agents still connect to it with their token. A connection to that socket cannot become a surface, whatever Origin it writes. Run (builtin): a socket with Origin: app://notes is refused with HTTP 403. A hub you start from the command line takes the same with reins-hub --no-surface-sockets. This closes the socket. It does not make the window's own port a secret from other pages that get into that window: the next point does that.
  • Register the window with its page. allow(win, { url }) takes the page's URL (compared without its #fragment), several, or a function. It is checked against the URL Electron reports for the frame when the page asks. A window that shows a file has to be registered this way: every local file has the one origin file://, so without the URL any other file that got into the window, by a link, a dropped file or a redirect, would be linked as your app. Run (builtin-file, windows): another local file loaded into the registered window is refused, and so is a file window registered without a URL. Pin navigation as well, as the example does in will-navigate; the URL check is what holds when something gets past that.
  • Agents outside the app reach the hub on loopback like any other hub. To let an agent with a shell find it with no path and no token on its command line, announce it the way reins-hub does. The example does it in ten lines with loadOrCreateSecret, announceHub and writeLauncher from @offensiveadhd/reins/hub; after that, node "$HOME/.reins/reins.mjs" reins_attach works from any folder. Run (tools-together).
  • An assistant inside the app needs no hub: build a Broker in the main process, pass (link, meta) => broker.accept(link, meta) as accept, and connect the assistant with linkPair() as in "Run the assistant in the tab".
  • One window is one surface. Call allow() for each window that should be one. A second request from a window closes the link it had.
  • Reloads and navigations. A port ends with its document. The new document runs your page code again, asks again, and appears at the hub as a new surface; an agent attaches again, and the person is asked again. The new grant starts at the level Ask, with no rules, and the chat transcript of the old document is gone. Run (builtin) with a reload.
  • A window that is not shown gets its link when it is shown, and none before: nobody could see a consent prompt in it. A page that asks first, as one does in a window created with show: false and shown on ready-to-show, simply waits for that moment. allow(win, { hidden: true }) links a window unseen, for an agent that needs no person under a policy that asks none. A view registered by its webContents (a WebContentsView) is held to the same rule: when its page asks, Reins asks Electron which window holds the view, links it when that window is shown, and gives a view that is in no window nothing. Run (windows), for a window and for a view. What the rule goes by is isVisible() of that window. It does not see a view that is hidden, of no size or covered by another view inside a window that is shown, nor a window that is shown behind others.
  • contextIsolation has to stay on. It is Electron's default, and the bridge needs it. In a window without it the preload refuses, and both sides are told why: the main process as a preload-error, the page as E_DENIED from electronLink(). sandbox is also Electron's default and what a page should run under; the bridge itself works without it. Run (windows).
  • Frames. Only the top-level frame of a registered window gets a port: the frame the window's contents report as their main frame, so the root of a fenced frame, which has no parent either, does not pass for it. The driver itself also refuses to connect inside a frame (policy.framed, SPEC section 12). Stand-ins.
  • <webview>. A guest page is the top-level document of its own frame tree, so its driver cannot see that another page embeds it and can draw over its consent prompt. The main process can: it refuses a guest unless you registered it with reins.allow(guestContents, { embedded: true }). Do that only when the embedding page is your own. A WebContentsView or BrowserView is placed by your main process, not by a page, and is treated like a window. Stand-ins.
  • Offscreen and background pages are refused: there is nobody to ask. Run (windows) for an offscreen page; background pages by stand-ins.
  • nav.go does nothing here. It takes http: and https: URLs only (SPEC section 9), so on a file:// or app:// page it answers E_DENIED. That stays as it is: a navigation inside an app is the app's business. Offer it as an action of your own (driver.action({ name: 'page.open', ... })), which then has a risk, a prompt and a place in the panel like every other action. What does work is the report: when your page changes its URL, agents hear it as a nav event, on file:// and app:// as on the web.
  • ESM main files. Electron holds back its ready event until the main module has finished loading. A top-level await app.whenReady() that comes after another await never returns (seen with Electron 45.4.1). Use app.whenReady().then(main), as the example does.
  • Not tested: a packaged app (app.asar), macOS, Linux.

2. Origins #

A hub admits surfaces by origin (SPEC section 5). A page that was not loaded over http(s) still has one, and Reins defines exactly what it is.

http://localhost:5173/... http://localhost:5173 that origin, http://localhost:*, or *
a file, file:///C:/app/index.html file:// file:// only
a scheme the app registered as standard, app://notes/index.html app://notes app://notes or app://notes:* only

The last column is why the rule is written out in the spec and not left to a URL library: Node says null where Chromium says file:// or app://notes, so a hub in Node and a broker in a page would disagree. urlOrigin() in @offensiveadhd/reins/core computes the origin the same way everywhere, and conformance/vectors/origins.json has the cases for another implementation. The host of an app origin is whatever Chromium keeps of it: app://-, app://. and a host with a trailing dot are origins it reports (observed once with Electron 45.4.1, with a probe that is not part of the repository's checks), and Reins takes them as they are.

Two entries need more than a name, because countless pages share the origin:

  • null admits every sandboxed frame on every website. A sandboxed frame, a data: page and a page on an unregistered scheme all send Origin: null. A hub whose socket admits null takes any of them as a surface, and such a connection may claim to be any app at any file: or app URL. Do not list null unless every surface has to prove a key (--require-key), or none comes over the socket. reins-hub prints a warning at start when it does.
  • file:// admits every local HTML file. Host and path are not part of the origin. A hub that admits file:// on its socket admits your app, and also any HTML file the person opens in a Chromium browser, which can then connect as a surface and receive what an agent sends it. reins-hub warns about this entry too.

Prefer, in this order: the in-process port of section 1 with surfaceSockets: false and the window registered with its URL; a scheme of your own (app://notes), which no web page and no file can have; a surface key (--surface-key <appId>=<file> with --require-key), which makes the hub demand proof from anything that connects.

  • Give the scheme a host. app://notes/index.html has the origin app://notes. Register the scheme with standard: true before the app is ready, or Chromium treats it as opaque and the origin is null.
  • An agent that is itself a page of the app connects from that origin, so list it on the credential: { "kid": "in-app", "key": "...", "origins": ["app://notes"] }.

3. Adopt an app you did not build #

reins-electron loads the driver into an Electron app from the outside, through the app's debugging connection. Nothing in the app is changed on disk.

Shell
# in the project that has the package
npx --no -- reins-electron -- "C:\Path\To\TheApp.exe"

Run (adopt-pipe) against the example app started as a foreign app (--foreign, no Reins in it). The lines are those of a real run, with the port and the two paths as they are by default:

reins-electron: started electron.exe with a debugging pipe (no port is open)
reins-electron: debugging connection open (Chrome/156.0.8078.100)
reins-electron: waiting for the app's first page, to learn its origin
reins-electron: levels the person may set in the panel: strict, ask (--levels offers auto and bypass)
reins-electron: page: origin app://notes
reins-electron: adopting; the app ends when this command ends
reins-electron: hub listening on ws://127.0.0.1:7346/ for agents (profile guarded)
reins-electron: adopting pages of: app://notes
reins-electron: the hub lists these pages as verified: this command alone holds the debugging pipe
reins-electron: token file: C:\...\.reins\token (agent kid "default", created)
reins-electron: agent launcher: node "C:\Users\you\.reins\reins.mjs" <tool>
reins-electron: page app://notes: ready

From then on the app is a surface like any other. In another terminal, or from an agent (run, tools-adopted):

Shell
node "$HOME/.reins/reins.mjs" reins_attach '{"reason":"tidy my notes"}'   # the app's window asks you
node "$HOME/.reins/reins.mjs" reins_observe
node "$HOME/.reins/reins.mjs" reins_ui '{"op":"type","target":"#note.input","text":"Water the plants"}'
node "$HOME/.reins/reins.mjs" reins_read '{"target":"#notes.list"}'

What it does:

  1. Starts the app with --remote-debugging-pipe. The DevTools protocol then runs over two inherited pipes. No port is opened, and no other program can connect.
  2. Hosts a hub (--port, default 7346) whose socket takes agents only, creates the agent token (--token-file, default .reins/token), announces the hub in ~/.reins and leaves the launcher there, exactly as reins-hub does.
  3. For every page of the app, now and later, runs the driver in each new document, in a JavaScript world of its own. A reload, a navigation and a new window are picked up as they happen. Run (adopt-pipe): reload, second window.
  4. Carries the driver's frames between the page and the hosted hub over the debugging connection. The page opens no socket, so its Content Security Policy does not matter. Run (adopt-pipe) with connect-src 'none'.

What an attached agent can do in an adopted app is everything a person can do with the mouse and the keyboard in that window. The app declared no actions, so the agent works through the UI tree: it sees every control the page exposes and can press, fill and scroll any of them. One Allow at attach covers all of it. There is no second question for "Send", "Delete" or "Approve", because to Reins those are buttons like any other. If the app is itself an agent that asks its user before it runs a tool, the attached agent can press that approval too. Adopt an app for an agent only when that is what you mean, and narrow it when it is not: --scopes observe,chat adopts an app to look at and talk about, not to operate.

Tool In an adopted app
reins_observe the controls of the page as a tree
reins_read the text between them: a paragraph, a message, a whole region, or the page
reins_ui clicks, typing, selection, scrolling and keys on every exposed element
reins_cursor, reins_show the agent's cursor, toasts and highlights
reins_chat the Chat tab, to talk with the person (section 5)
reins_act nothing to call: the app declared no actions

The person is asked in the app's own window before an agent attaches, sees the indicator while it is attached, and can pause or stop it, open the panel, switch single scopes off and talk to the agent (sections 4 and 5).

With the hub that reins-electron hosts, the app's own scripts cannot reach the driver or stand in for it. The driver's world shares the document with the page and nothing else, the function that carries its frames exists only in that world, which is named afresh for each run, and the hosted hub takes no surface over its socket. Run (adopt-pipe): from the page, typeof __reinsOut, __reinsIn, ReinsAdopt and Reins are all undefined. This does not hold when the pages join a hub elsewhere: see below.

Verified, or not. A surface is listed as verified when the hub knows what is at the other end of its link, and a page shows no "Unverified hub" mark when it knows its hub. For an adopted page both depend on one thing: who else can use the debugging connection.

The app is reached through The hub that reins-electron hosts lists the page as The page's prompt and indicator
the debugging pipe (the default) verified no mark
a debugging port (--debug-port, --attach) not verified say "Unverified hub"

A pipe belongs to the command alone: it started the app, put the driver there itself, and nobody else can reach either end. Through a port, every program on the machine can type and press in the app and speak on the page's link, so the command vouches for nothing, and the page takes what arrives for what it is. reins_surfaces shows the difference, a consent prompt names it, and chat-serve refuses a page that is not verified unless it is started with --allow-unverified (docs/CHAT.md). Run (adopt-pipe: verified; adopt-port: not verified, and the prompt and the indicator say so). With --hub the page is verified only by a surface key, and a key is not given to a page behind a port (below).

Option Meaning

Which origin, when you name none. Without --allow-origin the command takes the origin from the app's own pages, and only when there is no doubt. From the first page on it listens for a second; if every page that asked in that time has the same origin, that is the one, for this run. If they have more than one (a splash window from file:// and a main window from app://x, say), it does not guess by which loaded first: it stops, lists what it saw, and asks for --allow-origin. Two origins are never taken from a page and always have to be named: null, which says nothing about the page, and that of a web site that is not on this machine, which is something the app shows and not the app. (The rule is covered by unit tests; it was not seen in a real Electron.)

--match is an origin or a URL, not a piece of text. --match http://127.0.0.1:9120 adopts the documents of that origin. --match file:///C:/app/ adopts that folder and what lies under it, and a URL without a trailing slash matches itself and its sub-paths. Both the pattern and each document's URL are read as URLs and compared by origin and path; query and fragment take no part. So https://bank.example/login?next=127.0.0.1:9120 does not match, whatever it repeats. A pattern that is neither an origin nor a URL (a bare 127.0.0.1:9120) is refused at start, with how to write it.

The app ends with the command, and the driver lives no longer than it.

  • With the pipe, an app that reins-electron started ends when the command ends, however it ends: Chromium exits when its debugging pipe closes. Run (lifetime): the check closes only its two ends of the pipe, kills nothing, and the app exits.
  • With --debug-port there is no such tie, and the process the command started need not be the app: it may be a starter that runs the real program and exits, and an app may start itself again. So the command goes by the port. The app is the browser that answers there. The command does not end when the process it started does; when it ends, it closes that browser over the port (Browser.close), asks the port again, and says so in capitals and ends with 1 if something still answers. For a command that is killed, a small watcher process does the same: it learns of the command's end from a pipe between the two, and of the app from the port, and stays for ten seconds for an instance that comes up late. Neither of them ends a process by its id, which may by then belong to another program. Before it starts the app, the command checks that nothing answers on that port yet: otherwise it would adopt, and later close, an app it did not start. Run (lifetime): a killed command; a starter, with the command stopped and with it killed; and an app that starts itself again. In each case no process of the app is left and the port answers nothing. What this does not cover: the watcher itself being killed in the seconds it needs, and an app that takes Browser.close and stays (the command then tells you; the watcher can only write to the terminal it inherited). With the pipe neither can happen.
  • An app it attached to (--attach) is left running, and the driver is taken out of it. On Ctrl+C the command tells every document to disconnect for good, whatever carries its frames. Run (adopt-stop): the surface is gone at once and does not come back.
  • A command that is killed cannot say goodbye. Every document therefore holds a lease: the command renews it every 2 s, and a document that has not heard it for 10 s hands its driver no frame and sends none for it, asks the command once, and stops the driver for good when 5 s more pass without an answer. That is decided by the clock at the moment a frame arrives or is to leave, so it holds whether or not any timer fires: a script of the page can clear every timer of its document, the driver's world included, because timer ids belong to the document. Two clocks tick between frames so that a dead command is noticed without one, about 15 s after its last sign of life; one of them is a timer without an id, which such a script does not reach. Run (adopt-stop), with the page holding a socket of its own to a hub: after a kill the page leaves the hub within the lease; and after a script in the page's own world cleared every timer id and the command was killed, it leaves all the same, and an agent that comes in between gets nothing done. What is not promised is the 15 s when a page keeps its own thread busy without pause: then nothing runs in that document, the driver included, until it lets go.

The command prints the origin of each page it adopts or declines, never a URL: paths and queries are where tokens travel.

A debugging port #

Shell
"C:\Path\To\TheApp.exe" --remote-debugging-port=9222      # started by you, or by its own launcher
npx --no -- reins-electron --attach 9222

Run (adopt-port). Use this when you cannot start the app yourself. Know what it is: for as long as the app runs, any program on the machine that can open 127.0.0.1:9222 controls the app completely. It can read every page, run any script, press the Allow button of a Reins prompt, raise a permission level in the panel and type in the chat as you, because input sent through that port is real input to the page. reins-electron refuses a debugging port that is not on a loopback address, but it cannot make a loopback port private. Prefer the pipe.

That is why a page adopted through a port, with --attach or with --debug-port, is never called verified (above): its prompts and its indicator say "Unverified hub", the hub lists it as unverified, and chat-serve will not serve its chat unless you pass --allow-unverified and so accept that "the person" there may be any local program. For the same reason --surface-key-file is refused with a port: the key would sit in a page that every local program can read.

Joining a hub that is already running #

Shell
npx --no -- reins-hub --profile guarded --allow-origin app://notes --surface-key notes-app=.reins/notes-app.key --require-key
npx --no -- reins-electron --hub ws://127.0.0.1:7346 --app-id notes-app --surface-key-file .reins/notes-app.key -- "C:\Path\To\TheApp.exe"

The pages then connect to that hub as ordinary surfaces, next to your browser tabs, and it has to admit their origin. With --transport auto the page opens the socket itself where it may, and the hub sees the Origin that Chromium states. Where the page's Content Security Policy forbids the connection, reins-electron opens the socket instead, states the page's origin itself, and carries the frames over the debugging connection. Run (adopt-hub, adopt-hub-open) both ways, without a surface key:

reins-electron: page app://notes: connected through the page's own socket
reins-electron: page app://notes: connected through the debugging connection

The hub has to be on a loopback address; any other is refused before anything is dialled.

Join a hub with a surface key, as above. Without one, two things are true, and the command warns at start (run, adopt-hub):

  • The page cannot tell that hub from another program on its port, so the prompt and the indicator say "Unverified hub" (run, adopt-hub).
  • The hub admits by origin alone, and the app's own scripts have the same origin as the page. A script of the app, or anything injected into it, can open a socket to that hub and register as the same app, next to the real driver or in place of it, and then receives what an agent sends. The isolation of the driver's world does not help here: the hub cannot tell the two apart.

With the key the page verifies the hub, the session is sealed from the driver's world to the hub, and a hub that requires keys refuses the page's own scripts, which do not have it. Not run with a key. The key goes with the pipe only: with --attach or --debug-port the command refuses --surface-key-file, because whatever is in the page can be read through the port, and the pages stay unverified.

Apps that refuse #

  • No fuse turns this off. Electron's fuses (runAsNode, cookieEncryption, nodeOptions, nodeCliInspect, embeddedAsarIntegrityValidation, onlyLoadAppFromAsar, loadBrowserProcessSpecificV8Snapshot, grantFileProtocolExtraPrivileges, wasmTrapHandlers) do not mention --remote-debugging-pipe or --remote-debugging-port. nodeCliInspect is about --inspect, the Node debugger of the main process, which reins-electron does not use. (Read from Electron's fuses documentation, not tried.)
  • An app can still refuse in its own code: remove the switch (app.commandLine.removeSwitch) or quit when it sees it. Then reins-electron reports that the app did not answer on its debugging connection within 30 s. Which apps do this was not surveyed.
  • An app that is already running. Most desktop apps keep a single instance: a second start hands its arguments to the first and exits, and no debugging connection opens. Quit the app first, the tray icon included.
  • A launcher that is not the app. Some installers leave a small starter that runs the real program and exits (Update.exe --processStart ...). With the pipe, name the real executable: the pipe goes to the process the command starts, and a starter does not pass it on. With --debug-port a starter that passes its arguments on works, because the app is whatever answers on the port (run, lifetime), at the price of a port.
  • ELECTRON_RUN_AS_NODE in the environment turns an Electron executable into plain Node. reins-electron removes it for the app it starts.
  • webPreferences.devTools: false does not stop it. A window with DevTools switched off was adopted all the same (run, refusals).
  • <webview> guests are not adopted: they are separate targets, and their embedder can cover them.
  • Not tested: store builds that run in an OS sandbox (Mac App Store, MSIX), macOS, Linux.

4. The panel and permission levels #

While an agent is attached, the window shows the indicator "AI connected: <agent>". Its text is a button. It opens a panel with three tabs: Permissions, Activity and Chat. The normative text is in SPEC.md, section 12 ("Levels and rules", "The panel"); this section says what that is in an Electron window.

The panel belongs to the person at the window. It opens on their click and nothing else: no agent and no message can open it, close it or press anything in it.

In an app you built #

The panel is the driver's, so you get it by using the driver; there is nothing to add to the three pieces of section 1. What it offers follows from the policy:

The person can Where Needs
make one agent ask more: Strict Permissions, "How much it asks you" nothing: Strict and Ask are always there
make one agent ask less: Auto, Bypass the same place, with a second step the level in human.levels of the page's policy and of the hub's
set one action of one agent to Allow, Ask or Block Permissions, the list of your actions
switch one scope of one agent off and on Permissions, "What it may do"
end one agent's grant Permissions, Disconnect human.stop
see the last 50 commands and what let each run Activity
talk to the agents Chat the chat scope (section 5)

A grant starts at Ask, or at Strict where the person had set that for the same agent before. Raising to Auto or Bypass takes a second step that names the agent and lists the actions that would stop asking. The indicator then shows the level. What loosens lasts for one grant: Auto, Bypass, an Allow rule and a remembered approval end when the agent disconnects or the window reloads. What tightens stays with that agent for as long as the window's page lives: Strict, the person's Ask and Block rules and the scopes they switched off, until the person lifts them. Nothing the person sets makes an action run that your policy denies.

Run (builtin), in the Notes example, with the person played by real mouse and keyboard input:

PASS  built in: the indicator opens the panel, on the person's click
PASS  built in: raising the level to Auto takes the confirm step, which names the action that stops asking
        (the agent is told auto; the indicator reads "AI connected: “Smoke agent” (a1) Auto")
PASS  built in: the action that asked before now runs without a prompt, and a dangerous one stays refused
        (notes.publish ran unasked; notes.clear is E_DENIED at auto too)

The confirm step read: "Set “Smoke agent” (a1) to Auto? “Smoke agent” (a1) will then run this action without asking you, with any arguments: notes.publish".

To offer less, say so on both sides. Auto and Bypass are on offer only where the page's policy and the hub's policy both list them:

JavaScript
const policy = { profile: 'guarded', human: { levels: ['auto'] } };              // Strict, Ask, Auto: no Bypass
createDriver({ app, link: await electronLink(), policy });                       // page
await startHub({ agents, surfaces, surfaceSockets: false, policy });             // main process

human: { levels: [] } leaves Strict and Ask, and human: { panel: false } leaves the panel out (and with it the chat). One thing is particular to Electron: your main process can send a window real input (webContents.sendInputEvent, the debugger API). The panel keeps an agent from changing its own permissions. It cannot keep an app from pressing its own buttons, and does not try to.

In an app you adopted #

The adopted page has the same indicator and the same panel, drawn by the driver that reins-electron loaded. Run (adopt-pipe, adopt-levels).

By default the panel of an adopted app offers Strict and Ask, and neither Auto nor Bypass. That is the choice made here, and why:

  • A level decides one thing: whether an action the app declared asks the person first. An adopted app declares no actions. reins_ui, reins_observe, reins_read and the rest are not asked about one by one under any level; they are granted or not as whole scopes, at attach and in the panel's switches. So Auto or Bypass would let an agent do nothing it cannot do at Ask.
  • A red "Bypass" in the indicator of an app that was never written for agents would tell the person that something was unlocked when nothing was. The conservative default is the one that does not offer a switch wired to nothing. Strict and Ask stay, because they only ever tighten.
  • The person who starts reins-electron decides, not the default. --levels lists what the panel offers beyond those two:
Shell
npx --no -- reins-electron --levels auto -- "C:\Path\To\TheApp.exe"
reins-electron: levels the person may set in the panel: strict, ask, auto

The panel then offers Auto as well, and raising to it takes the same confirm step, which says truthfully: "No action of this app asks you about “Smoke agent” (a1) right now, so nothing changes at once." Run (adopt-levels). With --hub, the hub's own policy has to list the level too, or the panel does not offer it.

What the panel is for in an adopted app is the rest of it:

  • Scope switches. Switch ui off and the agent can look, read and talk, and can no longer click or type. Run (adopt-pipe): with ui off, reins_ui answers E_SCOPE; switched back on, it works.
  • Disconnect ends one agent's grant and leaves the others.
  • Activity shows what each agent did, without arguments or page text.
  • Chat (section 5).

To narrow what an agent can be granted in the first place, use --scopes. Both flags only ever narrow or label: the guarded profile, the consent prompt at attach, and Pause and Stop are not negotiable from the command line.

One warning belongs here because the test shows it: the "person" of the Electron check is a script that sends real input through a debugger, and it opens the panel, raises a level and types in the chat. Whoever holds an adopted app's debugging connection can do the same (section 8).

5. Chat #

The Chat tab of the panel is a room with the person at the window and every attached agent that holds the chat scope. CHAT.md is the guide to it, and it is the place to read what chat does not do and how to serve it safely. Everything there holds in an Electron window, built in or adopted. This section is the short version and what is particular here.

The person opens the panel, chooses Chat, types, and presses Enter. The agent that drives the window gets the message, does what was asked with its other tools, and answers; its answer shows in the tab under "AI agent" and its name.

The agent is It hears the person with It answers with
a script on the SDK page.on('chat', fn) page.chat.say(text), page.chat.status('working', note)
a model with the MCP tools reins_chat {"op":"wait"} reins_chat {"op":"say","text":"..."}
a model with a shell node "$HOME/.reins/reins.mjs" reins_chat '{"op":"wait"}' the same tool with "op":"say"
any program reins-tools chat-serve --exec <command>: one run per message, the text on standard input what the command prints

reins_attach asks for the chat scope by default, and the guarded profile grants it, so there is nothing to switch on. To leave chat out of an adopted app, start it with --scopes observe,ui,cursor,show.

Run (builtin, adopt-pipe), built in and adopted over the pipe:

PASS  adopted, pipe: what the person types in the Chat tab reaches the agent as the person's message
        (#1 from the person: Please add a note about milk)
PASS  adopted, pipe: the agent's answer shows in the tab, captioned as an agent's
        (#2; the tab reads: You 04:22 Please add a note about milk AI agent “Smoke agent” (a1) 04:22 Done: I added a note about milk.)

What to know in Electron:

  • It works under the app's Content Security Policy. In an adopted app the messages travel with every other frame over the debugging pipe; in an app you built, over the MessagePort.
  • In an adopted app, chat is how the person steers. The app has no actions to name, so "add a note about milk" in the chat, carried out with reins_observe, reins_ui and reins_read, is the whole interface. That is what the check above does.
  • A chat message approves nothing and changes no permission. If the agent then calls an action that needs approval, the window asks on its own prompt, and while that prompt is up the chat is hidden and takes nothing in either direction. Run (two-agents): "yes, publish it" in the chat, the prompt all the same, and chat.say answered E_BUSY until the person pressed Allow.
  • Agents hear the person. Whether they hear each other is the person's switch. Under the guarded profile it is off until the person turns "Agents can hear each other" on in the Chat tab; an app can decide it for its own page with policy.chatRelay, and the stricter of the page's and the hub's setting wins. Section 7 has the step.
  • The transcript lives in the page. A reload or a navigation ends it, like the grant. It is in the driver's closed shadow root: an agent does not get it from reins_observe or reins_read.
  • With --hub and no surface key, "the person at the page" is as sure as the page is, and the tools say so: the first line of a reins_chat result names a page the hub did not verify as such.
  • Pause does not stop the conversation. A paused agent cannot act and can still answer. Run (two-agents).

6.1 With the Hermes Desktop plugin (recommended) #

integrations/hermes-desktop is a Hermes Desktop plugin: one JavaScript module that Hermes evaluates in its window's own page, built with the Reins driver bundled in. It makes the Hermes window a surface that exposes nothing of its page and grants no ui scope. What an agent gets is three actions:

Action Risk Does
prompt.send {text} dangerous host.composer.submit(null, text): sends as if typed and entered. Asks you each time, and shows the whole prompt
prompt.draft {text} dangerous host.composer.setDraft(null, text): fills the message box, sends nothing. Asks you each time: the words are then one Enter from Hermes
reply.read safe Hermes's reply to the caller's own last prompt.send, {text, complete, truncated, session}, taken only from the events of the conversation the prompt went to. Another agent on the same window reads an empty reply

Both writing actions are dangerous, and that is the point of the word here: the level Auto waives the question for sensitive actions and never for dangerous ones. What each level means for this plugin:

Level prompt.send, prompt.draft reply.read
Strict ask, every time asks too
Ask (where a grant starts) ask, every time runs
Auto ask, every time: the same as Ask for this plugin runs
Bypass run unasked, unseen, whatever their length runs

Bypass is the one way to let prompts through without the question (the rule Allow for one of the two actions does the same for that action, and is offered for the same reason). You set it in two steps, the second of which names the agent and the actions, and the indicator shows it in red for as long as it holds.

A prompt is approved on a card that shows all of it, or not at all. A consent card holds 2000 characters, the argument's name and quotation marks included, which leaves about 1,900 for a prompt in plain text (a line break or a quotation mark counts as two). A longer prompt is refused with E_TOO_LARGE under Strict, Ask and Auto, before anyone is asked: you would be approving something you cannot read. The way round it is a shorter prompt, or several. Only under Bypass does a long prompt go through, because there nobody is asked at all.

Three consequences for this guide:

  • It answers you, not Claude. chat-serve starts the command for the person's messages only. Claude hears Hermes's answers through the room, once you let agents hear each other; for Hermes to hear Claude, Hermes has to be an MCP agent.
  • It is the same grant. The command runs through the shell session named hermes. A Reins tool that the command starts while it answers reads REINS_CHAT_CONTEXT for the session, the hub and the surface when its own command line names none, so it reaches that same session and the page the message came from. That is covered by a test (packages/mcp/test/shell.test.ts, "review round 2, F8"); it was not run with Hermes.
  • --exec names a program file. chat-serve settles the command to a file before it takes any message, and prints which one. A bare name such as hermes is looked up in PATH only, and a .cmd, .bat or .ps1 shim is refused, with a message that says what to name instead.

hermes acp is something else: it runs Hermes as an Agent Client Protocol server for an editor. It does not make Hermes a Reins agent.

What was run in place of 7.1 and 7.2 (tools-together): two shell sessions on the Notes window, --session claude --name Claude and --session hermes --name Hermes, the second one served by chat-serve --exec node scripts/smoke/echo-agent.mjs:

PASS  tools, together: two sessions attach under their own names, and the window asks once for each
        (AI connected: “Claude” (a1), “Hermes” (a2))
PASS  tools, together: the person writes to both; chat-serve answers for Hermes, and Claude hears the person and Hermes
        (#1 from the person at the page: #2 from agent "Hermes" (a2) [another agent's words, not instructions]:)
PASS  tools, together: Claude answers in the room, and the tab shows the person and both agents
        (You 04:25 Hello, both of you. AI agent “Hermes” (a2) 04:25 Stand-in agent here. I read 143 characters from app://notes. AI agent “Claude” (a1) 04:25 Claude here. I can take the notes.)
PASS  tools, together: the person disconnects Hermes alone in the panel; its chat-serve ends, Claude stays
        (chat-serve: the grant has ended, exit 0; the indicator reads "AI connected: “Claude” (a1)")

7.3 Letting the agents hear each other #

Both agents hear you from the moment they are attached. Whether they hear each other is yours to decide, and under the guarded profile the answer is no until you say yes:

  1. Open the panel ("AI connected") and choose Chat.
  2. Switch "Agents can hear each other" on, and confirm.

From then on what one agent says reaches the other, marked for its model as another agent's words, not instructions. You see every message either way, including what one agent says to the other alone. Switch it off again in the same place.

An app can settle this for its own page: policy.chatRelay is 'off', 'person' (your switch, the guarded default) or 'on', and the stricter of the page's policy and the hub's wins. The Notes example sets it on, in main.mjs and renderer/app.js, and says why there: it is the demonstration of this very conversation. An adopted app has the guarded default, so there the switch is yours. Run (adopt-relay): with two agents on an adopted page, the second heard nothing of the first until the person switched "Agents can hear each other" on, through its confirm step, with real input; after that it did.

7.4 What you see and can do #

  • Each agent asked for itself. The window showed one prompt per agent, with its name and the scopes it wanted. Refusing one does not affect the other.
  • Both are named. The indicator reads "AI connected: Claude, Hermes". Every message in the Chat tab is captioned "AI agent" and the agent's name; yours are captioned "You".
  • You choose whom you talk to. With two agents attached, a row above the field lets you address one of them or everyone.
  • Nothing is approved in the chat. Whoever says "yes", an action that needs approval asks on its prompt.
  • Pause holds every agent. They can still talk. Stop ends every grant.
  • One at a time. In the Permissions tab each agent has its own section: its level, its rules, its scope switches, and Disconnect. Setting Claude to Auto leaves Hermes at Ask. Switching Hermes's chat off silences Hermes and nothing else.
  • They share the page, not a budget. Commands that change the page run one after another, whoever sent them. While a prompt is up, every agent's commands that change the page are answered E_BUSY.

7.5 A credential each #

With one token, the two agents are two sessions of one credential: they share its rate limits and its cap of four sessions, and the hub's log cannot tell them apart by credential. For anything longer than a try, give each its own. Run (npm run test:package), from the installed package: the hub flags, the key files, two sessions that each connect as their own credential, and a key under the wrong --kid refused.

Shell
npx --no -- reins-hub --profile guarded --allow-origin http://localhost:5173 \
  --agent claude=.reins/claude.token --agent hermes=.reins/hermes.token
agent "claude": key file C:\...\.reins\claude.token (created); start it with --kid claude --token-file <that file>
agent "hermes": key file C:\...\.reins\hermes.token (created); start it with --kid hermes --token-file <that file>
agents: claude, hermes (no credential "default": an agent names its own with --kid)

Each agent then names its credential. --kid and --token-file are options of the launcher's tools, of the adapter and of chat-serve alike (the two lines below: not run):

Shell
claude mcp add --scope user reins -- node "$HOME/.reins/reins.mjs" mcp --kid claude --token-file "C:\full\path\.reins\claude.token" --name Claude
node "$HOME/.reins/reins.mjs" chat-serve --session hermes --kid hermes --token-file .reins/hermes.token --name Hermes --exec hermes chat --query-file - -Q

A key under the wrong --kid, or under none, is refused with E_AUTH. To give a credential a fixed display name or a scope cap, list it in a config file instead (--config hub.json, with name and scopes on each entry of agents); --kid picks it the same way. An Electron app that hosts its own hub, like the example, sets its credentials in the agents list it passes to startHub.

7.6 The whole thing as a script #

examples/electron/two-agents.mjs is the same situation with two scripted agents, Writer and Reviewer, and no model. It shows the room, the relay, and every control of 7.4, one step at a time.

Shell
cd examples/electron
npx electron .                 # terminal 1
node two-agents.mjs            # terminal 2: it tells you what to press and type
node two-agents.mjs --self     # or: it starts the app and plays the person too

Run (two-agents, and by hand with --self):

1. Both agents ask to attach. The window asks you once for each.
  ok      Writer is attached, to act and to chat (scopes observe act cursor show chat)
  ok      Reviewer is attached, to look and to chat (scopes observe chat)
  ok      the indicator names both (AI connected: Writer, Reviewer)
2. The room: what you type in the Chat tab reaches both agents.
  ok      your message reached Writer and Reviewer ("Please write a shopping note and have it checked.")
3. Relay: Writer does the work and tells the room; Reviewer hears it and answers Writer alone.
  ok      Writer added the note through the app's action and said so (note 1)
  ok      Reviewer heard Writer through the room, marked as an agent (from agent "Writer" (a1))
  ok      Reviewer read the app state and answered Writer alone (addressed to Writer)
  ok      Writer acted on it, and you saw the whole exchange (the tab shows Reviewer's line as "to Writer")
4. No approval by chat: "yes, publish it" changes nothing. The page asks on its own prompt.
  ok      Writer heard the "yes"
  ok      the page asks all the same, and the chat is hidden while it waits (chat.say answers E_BUSY while the prompt is up)
  ok      after you allowed it on the prompt, it ran (published 2)
5. Pause: a paused agent cannot act. It can still talk.
  ok      Writer was told it is paused, and its action is held (E_PAUSED)
  ok      Writer can still answer in the chat (#6)
  ok      after Resume it acts again (note 3)
6. Level: you set Writer to Auto. Its sensitive action stops asking. Reviewer stays at Ask.
  ok      Writer is told its level is auto; the confirm step named what stops asking
  ok      notes.publish now runs without a prompt, and Reviewer is still at ask (published 3)
7. Scope switch: you switch Reviewer's chat off. It can no longer speak, and hears nothing.
  ok      Reviewer is told, and its chat.say is refused (E_SCOPE)
  ok      your next message reaches Writer and not Reviewer (Writer answered)
8. Disconnect and Stop: you end Reviewer alone, then everything.
  ok      Reviewer's grant is gone, Writer's is not (Writer still reads the page)
  ok      after Stop no agent holds the page (E_NOT_ATTACHED)

8. Security notes #

The threat model is in SECURITY.md; rows T57 to T66 and the entries under "What Reins does not protect against" that name Electron or an adopted app are about this guide, and the "Review" section there says what two independent reviews of this feature found and what was changed. In short:

  • A debugging connection is total control. The driver's guardrails stand between the agent and the app. They do not stand between the app and the program that loaded the driver, which can do everything a person at the keyboard can: press Allow, open the panel, raise a level, switch a scope on, type in the chat as the person. The check in section 10 does exactly that to play the person. Adopt only apps you would let reins-electron control. Use the pipe. A debugging port extends that control to every program on the machine, which is why a page adopted through a port is never called verified, by the hub or by its own prompt, and gets no surface key (section 3).
  • In an adopted app, one Allow is the whole window. The agent presses what a person can press, the app's own "Send" and "Approve" included. For an app that is itself an agent, that is its tools. Narrow it with --scopes, or build the app's side instead (a plugin, as for Hermes in 6.1) so that an agent gets named actions and no clicks.
  • file:// is one origin for every file, and null for every sandboxed frame. Do not put either in the allowlist of a hub whose socket takes surfaces without requiring a key. In an app you build, register the window with its URL: the in-process port alone does not tell one file from another.
  • * does not cover Electron pages, on purpose.
  • Only the top-level page of a registered window gets a link, under the origin Electron reports and for the URL it was registered with. Do not register a <webview> guest as embedded unless you control what embeds it.
  • An adopted page's driver is out of the page's reach when the command hosts the hub: a world of its own, named afresh for each run. That protects the driver, its panel and its chat transcript from the page's scripts. Joined to a hub elsewhere without a surface key, the page's scripts can register at that hub themselves (section 3). And the page's document is shared either way: a hostile script in the app can change what the person and the agent see, as it can without Reins.
  • The driver ends with the command. A stopped command takes it out. A killed one is missed: a page that has not heard the command for 10 s handles no frame, and stops for good when the command stays silent, about 15 s after its last sign of life. The rule does not hang on a timer, which a script of the page could clear (section 3).
  • An app started with --debug-port is ended over its port, by the command or by its watcher, whichever process the app has become by then. No process is ended by its id.
  • A window that is not shown is not linked, whether you registered the window or a view in it. The rule goes by the window: a view hidden inside a shown window is not noticed (section 1).
  • An adopted app offers no level that loosens unless you say so. --levels is a decision of whoever starts the command; --scopes narrows what any agent can be granted.
  • Chat is data. What the person types reaches a model marked as the person's request about this page, not as its operator's instruction; what another agent says is marked as that agent's words. Neither approves anything, and agents hear each other only once the person said so.
  • A plugin runs with the app's authority. The Hermes plugin of 6.1 is code in Hermes's own page, next to every other plugin. It is not a boundary.
  • A prompt to an agent app is a dangerous action. The Hermes plugin asks about every prompt under every level but Bypass, shows all of it or refuses it, and gives the reply to the agent that asked and to no other (6.1).

10. What was tested #

npm run test:electron runs scripts/smoke-electron.mjs against the example app with a real Electron. It is not part of npm test, and the repository never installs Electron by itself:

Shell
cd examples/electron && npm install && cd ../..
npm run build
npm run test:electron
npm run test:electron -- builtin adopt-pipe                      # only these scenarios
ELECTRON_BIN=/path/to/another/electron npm run test:electron     # the same checks on another build

It needs a person: to press Allow, to open the panel, to choose a level, to type in the chat. scripts/smoke/electron-person.cjs plays one inside the app. It finds the prompt and the panel through the accessibility tree and uses real mouse and keyboard input, and it prints what each prompt and each confirm step said. Where a consent card is taller than the window, the card says "Scroll to the end to review everything before allowing" and its Allow waits for that; the person then turns the mouse wheel over the card until the hint is gone, says in its log that it scrolled, and presses. No model is called anywhere. The script's first lines name the Electron binary and print its Electron, Chrome and Node versions, so a run says what it ran with.

103 checks, all passing on Windows 11 with Electron 45.4.1 (Chrome 156.0.8078.100, Node 24.22.3), and the same 103 with Electron 44.10.2 (Chrome 152.0.7977.169, Node 24.22.2), the runtime Hermes Desktop ships, by setting ELECTRON_BIN to its electron.exe. The numbers are those of the last run before this was written; run it to get yours. Its last line says whether every check passed, and a failed attach prints what the person at the window saw and did.
