Reins protocol conformance suite

What the conformance suite checks, how to run it and what it does not cover. Rendered from conformance/README.md.

This page is conformance/README.md, rendered from the repository at build time. It is the text the project maintains, not a copy.

This folder checks an implementation of Reins against docs/SPEC.md (protocol 0.1). The existing tests under packages/*/test exercise the reference implementation's own code paths; the tests here are written from the specification instead. Each test name starts with the id of the requirement it checks, and requirements.json maps every requirement to its spec section and its tests.

Running #

npm run test:conformance

This runs vitest run conformance. No build step is needed: vitest.config.ts maps the @reins/* imports to the package sources. Every hub listens on port 0 and every temporary file goes under the OS temp directory, so the suite can run next to a hub on port 7346. A full run takes about half a minute; three tests wait out the hub's 5 s timers on purpose (HS-9, HS-17) or create 64 connections (CAP-2).

To regenerate the vectors after a spec change:

node conformance/tools/make-vectors.mjs          # write vectors/*.json
node conformance/tools/make-vectors.mjs --check  # exit 1 if a file would change

node conformance/lib/spec-text.mjs prints the normative sentences and section 14 rules the meta-test reads from SPEC.md; node conformance/lib/test-names.mjs prints the test titles it knows.

Using the vectors from another implementation #

Each file in vectors/ is self-describing: spec names the section, formula or layout restates the rule, and note explains the cases. Every detail the vectors depend on is now written in SPEC.md; no vector relies on the reference implementation for a rule the spec leaves open. Byte strings are hex, base64url values are unpadded (RFC 4648 section 5).

file how to use it
auth.json For each case compute HMAC-SHA256(key, peerInput) and HMAC-SHA256(key, hubInput) over UTF-8 bytes, base64url; compare with peerProof and hubProof. The third case has a non-ASCII kid.
seal.json Derive th, kPeer and kHub from key, nonce, cnonce, challengeText, helloText, welcomeText; seal the peerToHub messages in order from sequence 0 and compare with wire / wireHex; do the same with hubToPeer; open the wire messages and expect the payloads. macOnly gives MACs at large sequence numbers. illFormed must never be sealed or opened.
pointer.json Encode frame and compare with hex; decode hex and compare with frame; clamp and rounding cases check the encoding of fractions and dt; invalid must be refused.
merge-patch.json apply: RFC 7396 appendix A. diff: any patch P with apply(from, P) == to passes. equal: no patch at all; some cases differ only in null properties, which read as absent.
ui-delta.json apply: apply ops to nodes, expect expect. diff: your diff, applied to prev, must give next, with every del first. render: the compact tree text and single node lines. renderDelta: delta text rendered against prev.
methods.json Method to scope table, HUB_METHODS, READ_ONLY_METHODS, CHAT_SPEAK_METHODS, scope intersection.
policy.json Profile table with its defaults (levels, panel and chatRelay included), override precedence, strictness order.
levels.json rows: split each row on spaces into columns; from the policy decision, the action's risk, the level, the rule (- for none) and the levels on offer (joined by +), your decision for an act request must give outcome, and by and remember where they are not -. c1: a request with c:1 counts as the decision in counts. offered: the levels on offer from the two human.levels lists (strict and ask always). hub: the hub's decision for an action as a surface reads it from decisions in attach; anything missing or malformed is confirm. allowRule: where the rule allow may be set.
chat.json text.cases: trim the text (unit and times stand for a repeated unit between before and after); with ok it is kept and has length, otherwise chat.say answers E_BAD_ARGS. statusNote.cases: the note as it is kept, or refused. message: take the valid messages, keeping only fields, and drop the invalid ones. audience.rows: split each row on spaces into columns; from the agents in the room, the agents among them that hear each other, who speaks and whom they address (person for the person alone), your decision must give outcome and result. relay: the three values of chatRelay, and for every pair the stricter one. auditDigest: the canonical JSON and the unkeyed digest a chat text is recorded with, whatever else was sent with it. lines: a chat text as the `
manifest.json Canonical JSON (with canonicalCases for key order and numbers) and digest of a manifest, and the prompt card of SPEC section 7.
audit.json An unkeyed and a keyed audit chain to verify; args is SHA-256, or HMAC under the key, of argsCanonical.
errors.json, limits.json The complete error code list of SPEC section 6, and numeric limits the spec states.
origins.json urlOrigin: the origin of each url (JSON null: not a URL; the string "null": opaque). allowed: whether entries admit origin. surfaceUrl: whether url may be hello.surface.url on a connection from origin.

The hub tests in hub-*.test.ts are black-box at the wire level: to run them against another hub, replace startTestHub in lib/hub.ts with code that starts that hub on a free port with the same configuration (credentials, allowed origins, policy, limits) and exposes its audit records. Tests that configure the hub through BrokerConfig options or read memoryAudit records depend on the reference configuration shape.

Coverage limits #

These requirements are not checked, or only partly:

  • TR-2 (refuse a non-loopback remote address): needs a second network interface; the test only shows loopback clients are served.
  • S14.3, owner-only files: checked by POSIX mode only; on Windows the ACL is not inspected (the test is skipped there). The token file written by the CLI is not covered.
  • Section 5: the inbound bound before authentication (16 messages, 64 KiB) and dropping what a peer sends after a failed proof race the hub's asynchronous proof check, so they are not tested at the wire; the link bound (4096 messages, 16 MiB) is not covered.
  • Section 11 drop policy (droppable frames above 256 KiB of surface backlog, stall at 1 MiB), receiver playback, coalescing on the sender, and Pause and Stop discarding queued points: need control of socket buffers or animation frames; only playbackRate and the credit batching are checked.
  • Section 9 ordering, command batching per animation frame (6 ms), cursor glide timing, and "checks hold across waits": timing-dependent, not covered.
  • Section 12: the 500 ms arming of Allow, Allow waiting for a tall card to be scrolled, the escaping of invisible code points on the card, the "Request withdrawn" notice, the indicator above the prompt's backdrop or inside a modal dialog or fullscreen element, and human.yieldMs after real input (happy-dom input is never trusted): not covered beyond what S14.10 and S14.11 check.
  • Section 12, the panel: happy-dom has no layout and no trusted input. The LV- surface tests mark their own events as trusted to play the person, so they show that unmarked events do nothing, not that a browser marks events correctly. Where the panel sits (beside a consent card on a wide viewport, under its backdrop on a narrow one, inside a modal dialog or a fullscreen element), the "Always allow" step on a card and the colours of the indicator are not covered here; the driver's own tests (packages/driver/test/levels.test.ts) cover their logic.
  • Section 12, the overlay and the page: happy-dom has no top layer, no painting, no native isTrusted and no IntersectionObserver. LV-24 to LV-26 check the stylesheet's text, the effects a style engine reports on an ancestor of the host, and that a late hook is handed no listener. LV-29 plays keys as events it marks trusted and moves the focus itself, since happy-dom does not move it on Tab; LV-32 reads zoom from a computed style it sets, and LV-35 uses a stand-in for the Popover API. That page CSS leaves every pixel of the overlay as it was, that the host is last in the top layer (also above a page's own popover and inside a modal dialog), that a forged or borrowed event moves nothing where the browser's own getter is read, where a real key or click lands (Tab and Enter typed for the page, a word and Enter, Tab, Enter, Tab, Enter), that ::before, ::after, ::marker and ::first-letter rules of the page add no box to the host, and that zoom and display: none on html stop commands, is checked in a real Chromium by node scripts/browser-check.mjs (npm run test:browser; it skips when no Chromium is found unless --require is given). The driver's packages/driver/test/hardening.test.ts covers the logic of the top layer and of the visibility observer with stand-ins.
  • Section 12, chat: happy-dom has no layout and no trusted input. The CH- surface tests set the composer's value and mark their own input, key and click events as trusted to play the person, so they show that unmarked events and a value set by script send nothing, not that a browser marks events correctly or that an input method behaves. How the tab looks (light and dark, a narrow viewport), the scroll position of the transcript, the lapse of a status after 2 minutes, what a screen reader says, and the focus that returns to the composer after a command are not covered here; the driver's own tests (packages/driver/test/chat.test.ts) cover the logic of the last two. That a page's own script can read the composer and the transcript and alter what is sent (docs/SECURITY.md, "What Reins does not protect against") is stated, not tested: the tests show what an agent cannot do, and that ordinary bubbling listeners see nothing. That the composer takes no input while an app action runs is tested with an action that writes into the field, not with a browser's execCommand.
  • Section 13: fail-closed on more than 1000 queued records, lost summaries, a peer closed for not reading, refusing to continue a log whose chain or head does not verify (fileAudit), and the 32-agent cap.
  • Sections 3 and 15, Electron: nothing here starts Electron. What Chromium sends as Origin, the port crossing contextIsolation, the debugging pipe, the driver in a world of its own under a page's Content Security Policy, and consent, the panel, a level and the chat in a real window with real input are checked by npm run test:electron, which is not part of this suite (see docs/ELECTRON.md).
  • Section 15: CLI behaviour (token files, secret-file checks, flags, escaping of page text), the [unverified hub data] marking of the MCP adapter, and the agent SDK beyond its pointer credit are not covered. Of reins_chat, the 150 s cap of a wait is checked as a constant and with a mock clock in packages/mcp/test/chat.test.ts, not by waiting. The read of the room every 45 s while a wait is in flight is tested there too, and against a real hub whose clock is moved in examples/kiosk/test/chat.test.ts. Of chat-serve, the command line, the timeout and the failure notices are covered in packages/mcp/test/chat-serve.test.ts, not here. CH-29 shows here, on the machine the tests run on, that a process a command left running when it exited is ended. What a Windows job object holds beyond that (a process whose parent has exited, a tree that goes on growing, one started by cmd.exe, PowerShell or Python, a request to leave the job refused) and that nothing is run where no job object can be made, is covered by the tests named review round 2, F3 in that file, on Windows only; the process-group path is covered by the tests there that are not Windows-only, on the machine they run on. That down and up leave the process of a stale announcement alone, that up prints the hub's origin warnings, and that an option a running session cannot take is refused, are covered in packages/mcp/test/shell.test.ts; what a system reports as a process's creation time is asked for real only on the machine the tests run on. No test runs a model, and none runs a harness: the Claude Code subagent in integrations/ was not run under Claude Code.

Tests marked it.fails are places where the implementation does not do what the spec says; each carries a // SPEC MISMATCH: comment.
